# Open questions

Each entry has the exact command or file needed to resolve it. Numbers are referenced from
`docs/architecture/*` and the inventories.

## Blocking the Windows port (answer before Gate 2)

**OPEN QUESTION #1 — Is the Windows app supposed to include the MCP server?**
The MCP server is a separate executable inside the app bundle (`project.yml:83-93`), shares
`Core`/`Features`, and is launched by the *agent*, not the app (`Sources/MCP/main.swift:7-17`).
A Windows port must decide: one binary with an `--mcp` flag, a sibling `ohmyandroid-mcp.exe`, or
app-only. This decides the project layout, the installer contents and whether
`mcpb`/`server.json` get a `win32` platform.
Resolve by: product decision. Evidence needed: none (it is a choice).

**OPEN QUESTION #2 — Does the fork keep the macOS app buildable?**
`docs/assumptions.md` A2: the UI needs macOS 26 APIs. If the fork keeps `Sources/` as the reference
implementation, it must stay *readable*, not necessarily *buildable*, on Windows CI.
Resolve by: declaring intent; optionally `git tag upstream-baseline-9f37391` plus a frozen
`reference/` copy (see `docs/windows-port/05-repo-restructure.md`, not yet written).

**OPEN QUESTION #3 — Is bundling Google `platform-tools` acceptable?**
Upstream deliberately does not bundle `adb` (`Sources/Core/Android/AndroidSDK.swift:3-6`).
A Windows-first app almost certainly wants to ship `platform-tools` or download it on first run.
Resolve by: reading Google's SDK terms + the `platform-tools` LICENSE. Files needed:
`platform-tools/NOTICE.txt` from any SDK install. `UNVERIFIED` — no SDK on this machine.

## Blocking accurate documentation

**OPEN QUESTION #4 — Per-tool argument contracts of the 18 MCP tools.**
Only the tool *names*, descriptions and adb call lines were read (see `docs/coverage.md`).
Resolve by: reading `Sources/MCP/Tools/DeviceTools.swift`, `ScreenTools.swift`, `InputTools.swift`,
`AppTools.swift` (except :116-151), `DataTools.swift`, `EmulatorTools.swift` in full, and
`Sources/MCP/Format/UITreeText.swift`.

**OPEN QUESTION #5 — Layout Inspector measurement semantics.**
`Sources/State/LayoutInspectorStore.swift` (142 L) and
`Sources/UI/Layout/LayoutInspectorView.swift` (319 L) define what "gap", "padding" and the
design-overlay alignment actually mean. Not read.
Resolve by: reading both files, plus `Sources/Core/Imaging/PixelSampler.swift`.

**OPEN QUESTION #6 — What exactly does `ImageScaler` do?**
Assumption A4. File: `Sources/Core/Imaging/ImageScaler.swift`. Resolve by reading it and measuring
one screenshot.

**OPEN QUESTION #7 — Does docking to the emulator window work for anything but `qemu-system*`?**
`Sources/Windows/PanelController.swift:65-69` matches running apps whose executable name starts with
`qemu-system`. Whether the modern emulator still uses that name, and whether `EmulatorWindowTracker`
matches by title or by pid, needs `Sources/Windows/EmulatorWindowTracker.swift` (not read).
Resolve by: reading that file; run the emulator and watch the panel dock.
